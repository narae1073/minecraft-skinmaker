## 1. 개요

스킨메이커는 **인물 사진 한 장을 마인크래프트 64×64 RGBA 스킨 PNG로 바꾸는 도구**다.
핵심은 “사진을 축소해서 붙이는 것”이 아니라, 사진에서 **믿을 수 있는 정보만 뽑아**
64×64라는 아주 좁은 픽셀 문법으로 **다시 그리는 것**이다.

왜 그렇게까지 하느냐 하면, 64×64 스킨은 표현력이 극단적으로 제한되어 있기 때문이다.

- 한 레이어에서 실제로 칠할 수 있는 픽셀은 classic 기준 **1,632개**뿐이다.
- 얼굴 앞면은 **8×8 = 64픽셀**이다. 눈 4픽셀, 입 1픽셀만으로도 표정이 달라진다.
- 옷 한 벌을 그릴 수 있는 공간은 몸통 8×12, 팔 4×12, 다리 4×12 정도다.

그래서 이 시스템은 역할을 이렇게 나눈다.

| 역할 | 누가 | 잘하는 것 | 잘 못하는 것 |
|---|---|---|---|
| 의미 분류 | VLM(Visual Language Model) | “티셔츠인지 재킷인지”, “무늬가 있는지” | 정확한 색, 픽셀 단위 위치, 일관성 |
| 위치/영역 | SCHP 인체 파싱, 얼굴 기반 기하 | 사람의 부위를 마스크로 분리 | 옷 종류나 브랜드 같은 의미 |
| 색 측정 | 코드(OpenCV/NumPy) | 같은 입력에 같은 색, 중앙값/군집 | 애매한 맥락, 가려진 대상 |
| 픽셀 생성 | 파라메트릭 렌더러 | 64×64 규격, 좌우 대칭, 게임 호환 | 사진에 없는 디테일 |
| 품질 보증 | `validate_image`, 후보 검증 | 게임에서 깨지는 출력 차단 | 주관적 “닮음” |

이 문서에서 말하는 **보정(calibration/correction)** 은 카메라 렌즈 왜곡 보정 같은
좁은 의미가 아니다. **통제되지 않은 사진과 모델의 추정값을 64×64 스킨의 좌표계·색
공간·의미 체계에 맞게 정규화하고, 근거가 약하면 그럴듯한 값을 지어내는 대신
기권하거나 안전한 기본값으로 폴백하는 모든 결정론적 장치**를 뜻한다.

### 먼저 알아둘 용어

| 용어 | 뜻 |
|---|---|
| VLM | 이미지와 텍스트를 함께 이해하는 모델. 여기서는 “무엇을 입었는지”만 묻는다. |
| SCHP | 사람의 신체 부위를 픽셀 단위로 분류하는 인체 파싱 모델. |
| 마스크(mask) | “이 픽셀은 바지”, “이 픽셀은 머리카락”처럼 부위를 표시한 지도. |
| bbox | bounding box. 얼굴이나 머리카락이 차지하는 사각형 영역. |
| enum | 정해진 선택지. 예: `tee`, `hoodie`, `jacket` … |
| 폴백(fallback) | 확신할 수 없을 때 다른 경로나 기본값으로 물러나는 것. |
| 스텐실(stencil) | 머리를 8×8 격자 어디에 칠할지 정한 불리언 격자. |
| L1 / L2 | 스킨의 기본 레이어(layer 0) / 오버레이 레이어(layer 1). |
| UV | 64×64 텍스처의 어느 사각형이 3D 모델의 어느 면에 붙는지를 정한 좌표. |
| 결정론적 시드 | 같은 입력이면 항상 같은 노이즈가 나오게 하는 난수 씨앗. |

## 2. 전체 흐름

### 2.1 논리 단계와 실제 실행 순서

문서와 설계 번호는 **S0 → S1(색) → S1b(파싱) → S2(분류) → S3(렌더) → S4(후보)** 순서로
읽기 쉽게 붙어 있지만, **웹과 CLI의 실제 실행 순서는 다르다**.

웹 API는 S2를 먼저 호출한다. VLM이 돌려주는 `hair_bbox`(머리카락 영역)를 S1의 머리색
샘플링에 사용해야 하기 때문이다. 실제 순서는 다음과 같다.

```
S0  입력 게이트 (얼굴/품질)
 → S2  VLM 분류 (무엇을 입었나 + hair_bbox)
 → S1b SCHP 파싱 (부위 마스크; 모델이 없으면 생략)
 → S1  색 관측 (WB, 군집, 마스크 국소화, 증거)
 → S3  렌더 (64×64 픽셀)
 → S4  후보 (불확실한 필드만 변형, 1~3개)
 → 검증/저장/표시
```

> **주의**: “S1이 S2보다 먼저”라고 설명하는 문서가 있지만, 그것은 개념적 번호다.
> 코드의 실제 호출 순서는 `backend/app.py`의 `generate_skin()`과 `skinmaker/s4.py`를
> 보면 S2 → S1b → S1이다. 이 문서는 실제 순서를 기준으로 설명한다.

### 2.2 한 장의 사진이 지나가는 길

```
[업로드]
  │  파일 형식/용량/레이트리밋 확인
  ▼
[S0] YuNet 얼굴 검출 ── 얼굴 없음 → 422 종료
  │  품질 플래그(흐림/어두움/작음/과다노출/저채도)는 "거부"가 아니라 "파라미터"
  ▼
[S2] 얼굴 기준 크롭 → VLM 2회 질의(정순/역순)
  │  14개 enum + hair_bbox
  │  검증/강제(coerce)/교차 규칙/불확실성
  ▼
[S1b] SCHP 마스크 (선택) ── 실패/모델 없음 → 조용히 밴드 경로
  │  Pants/Skirt/Dress/Hair/Shoes/Bare-legs
  ▼
[S1] 색 관측
  │  스킨 앵커 WB, 피부/머리/상의/하의 색, 배경 제거,
  │  하의 캐스케이드, 마스크 국소화, 줄무늬/원단, 증거 플래그
  ▼
[S3] 파라메트릭 렌더
  │  resolve(확신 게이트) → 하의 정책 → 패턴/구조 → 머리(reference pack) → 팔다리 → 노이즈 → 후드
  ▼
[S4] 후보 1~3개
  │  2차 질의와 다른 필드만 변형, 각 후보 validate_image
  ▼
[저장/응답]
  │  input/skins/skins_flat/steps URL + 요약/카테고리 JSON
  ▼
[웹] 결과 인라인 + 3D 뷰어(마우스 전용·고정 조명), 편집 모달, 분류 패널, 처리 과정 시트
```

### 2.3 단계별 입출력 요약

| 단계 | 입력 | 핵심 처리 | 출력 |
|---|---|---|---|
| S0 | 이미지 파일 | 얼굴 검출, 품질 측정, 구도 판정 | `PhotoInput` (얼굴 상자, 품질, degrade 플래그) |
| S2 | `PhotoInput` | 얼굴 기준 크롭, VLM 2회, 스키마 검증 | `Classification` (14필드, 불확실성, raw 응답) |
| S1b | 원본 이미지 | SCHP 512×512 추론 → class map | 부위별 마스크 또는 `None` |
| S1 | 이미지 + 마스크 + hair bbox | WB, 군집 대표색, 배경/그림자 제거, 증거 수집 | `ObservedColors` |
| S3 | `ObservedColors` + `Attributes` | 색/하의/패턴/구조/머리 결정, 픽셀 렌더 | `SkinCanvas` (64×64 RGBA) |
| S4 | 위 둘 | 불확실 필드 변형 후보, 검증 | `Candidate` 1~3개 |
| 저장/API | 후보들 | PNG 저장, URL/JSON 생성 | 웹 응답 |

## 3. 주요 단계별 설명

### 3.1 S0 — 입력 게이트: “이 사진으로 시작해도 되는가?”

**목적**<br>
사진에서 주인공 얼굴을 찾고, 그 얼굴의 품질을 재서 “거부할지”가 아니라 “얼마나
보수적으로 그릴지”를 정한다. 이 파이프라인의 **유일한 하드 거부는 얼굴 미검출**이다.

**입력**<br>
사용자가 업로드한 이미지 파일. 서버는 임시 파일로 저장한 뒤 Pillow/OpenCV로 읽는다.

**처리**

- YuNet 얼굴 검출기로 얼굴 후보들을 찾는다.
- 후보가 여러 개면 **면적이 가장 큰 얼굴**을 주인공으로 고른다. 면적이 최대의 90%
  이상으로 비슷하면 화면 중앙에 가까운 쪽을 고른다 (`select_face`).
- 얼굴 상자에서 밝기, 선명도(라플라시안 분산), 채도, 얼굴 픽셀 면적을 잰다.
- 다음 플래그를 만든다: `blur`, `dark`, `bright`, `small`, `flat`.
- 얼굴 높이 / 이미지 높이 비율로 **전신 여부**를 판정한다 (기본 임계값 0.12).
- 포즈 추정도 시도하지만, 현재는 `mediapipe`가 제거되어 있어 항상 `None`이다.

**출력**<br>
`PhotoInput(path, image, face, quality, degrade, pose)`.

**중요한 제약**

- 품질 플래그는 **거부 사유가 아니다.** 흐리거나 어두운 사진도 “같은 그림을 더
  보수적으로” 그린다. 거부하면 사용자 경험이 나빠지고, 조명 문제는 렌더 정책으로
  흡수할 수 있기 때문이다.
- 얼굴이 너무 작아 품질 측정이 불가능하면 `measured=False`가 되고 `small` 플래그가
  붙는다. 이 경우 머리색 샘플링을 생략하는 등의 보수화가 일어난다.
- 구도 판정은 이후 S2 크롭 해상도(초상 768 / 전신 1536)와 하의 폴백 정책에 함께
  쓰인다. 같은 “전신” 기준을 공유해야 분류와 렌더가 어긋나지 않는다.

### 3.2 S2 — VLM 분류: “무엇을 입었는가?”

**목적**<br>
사진의 옷 종류·무늬·머리 길이/스타일·후드·수염·안쪽 옷·넥타이·구조(지퍼/단추/칼라/
주머니)·대칭을 **정해진 선택지(enum)** 로 분류한다. 색은 여기서 묻지 않는다.

**입력**<br>
`PhotoInput`과 그 얼굴 상자. 얼굴 주변을 넓게 잘라 모델에 보낸다.

**처리**

1. **크롭**: 얼굴 폭의 1.7배를 좌우로, 얼굴 높이의 1.25배를 위로 확장하고, 아래는
   최소 4배 또는 이미지 하단까지 내린다. 전신이면 긴 변을 1536px, 아니면 768px로
   줄인다. 얼굴만 보면 하의와 손이 잘리므로 일부러 넓게 잡는다.
2. **프롬프트/스키마**: `skinmaker/attributes.py`가 단일 원천이다. 14개 필드와
   `hair_bbox`(0~1000 정규화 좌표)를 요청한다.
3. **이중 질의**: 같은 이미지에 대해 필드 순서를 정순/역순으로 두 번 묻는다. 온도는
   0으로 두어 가능한 한 결정적으로 만든다.
4. **검증/강제**: 응답이 enum에 없거나 없으면 기본값으로 채우고 `coerced`/`missing`에
   기록한다. `top_garment=none`이면 소매/무늬/여밈/칼라/주머니를 `none`으로 강제하는
   교차 규칙을 적용한다.
5. **합의/불확실성**: 두 응답이 다르거나, 강제/누락이 발생한 필드를 `uncertain`으로
   표시한다. 병합은 필드별로 첫 응답의 유효값을 우선하고, 첫 응답이 무효/누락이면
   두 번째 유효값으로 채운다. 두 번째 응답은 **후보 변형의 근거**로도 쓰인다.
6. **bbox 변환**: 0~1000 정규화 좌표를 원본 픽셀로 되돌리고, 뒤집힌 좌표는 정렬하고,
   너무 작은 bbox는 버린다.

**출력**<br>
`Classification(attributes, uncertain, raw_first, raw_second, hair_bbox_px, ok, …)`.

**중요한 제약**

- **VLM에게 색을 묻지 않는다.** “회색 셔츠를 네이비라고 부르는” 문제가 실제로
  확인되었고, 색은 코드가 재는 편이 훨씬 정확하다.
- 두 번째 질의가 실패해도 요청 전체를 실패시키지 않는다. 첫 답만으로 진행하고
  후보 수가 줄어든다.
- API 키 누락 같은 `TransportError`는 500이 아니라 구조화된 503으로 변환된다.
- VLM 응답은 “정답”이 아니라 **불확실성을 포함한 증거**다. 이 점이 뒤의 후보 생성과
  UI 표시로 이어진다.

### 3.3 S1b — SCHP 인체 파싱: “그 옷/머리/신발이 어디에 있는가?”

**목적**<br>
색을 잴 위치를 정확히 잡기 위해 사람의 부위를 픽셀 마스크로 분리한다. 밴드(얼굴
비례 사각형)만으로는 전신샷에서 상의/하의/배경이 섞인다.

**입력**<br>
원본 이미지. 웹에서는 요청당 한 번만 추론하고, 그 마스크를 색 추출과 처리 과정
시트가 공유한다.

**처리**

- 이미지를 512×512로 줄여 정규화한 뒤 SCHP ONNX 모델에 넣는다.
- 클래스 맵을 원본 크기로 NEAREST 리사이즈한다.
- 사용하는 클래스: Pants(6), Skirt(5), Dress(7), Hair(2), Shoes(9/10),
  Bare-legs(12/13), Face(11) 등.
- 치마 밑단은 사진 속 위치를 다리 텍스처의 0~8행(신발은 9행부터)까지의 천 길이로
  환산한다. 함수는 1~9를 반환하고, 렌더는 9를 신발 시작과 같게 다룬다.

**출력**<br>
원본 크기의 `uint8` class map, 또는 `None`.

**중요한 제약**

- 모델/런타임이 없거나 추론이 실패하면 **예외를 던지지 않고 조용히 `None`**을 돌려준다.
  호출부는 얼굴 비례 밴드/캐스케이드 경로로 폴백한다.
- `SKINMAKER_PARSING=0`으로 끌 수 있다. 기본은 켜짐.
- 마스크는 “옷의 종류”를 알려주지 않는다. “이 픽셀이 바지 클래스다”까지만 말한다.
- 마스크로 국소화한 색은 **WB 이전 원본**에서 잰다. 이 선택은 뒤에서 설명한다.

### 3.4 S1 — 색 관측: “정확히 어떤 색인가?”

**목적**<br>
사진에서 피부·머리·상의·하의·신발·홍채·안쪽 옷·타이·겉옷의 대표색을 재고, 그
측정이 얼마나 믿을 만한지 함께 기록한다.

**입력**<br>
원본 이미지, 얼굴 상자, VLM의 `hair_bbox`, 선택적으로 SCHP 마스크.

**처리**

1. **화이트밸런스(WB)**<br>
   얼굴의 볼/코 영역에서 피부 크로마를 재고, 그 크로마를 기준 피부색
   `SKIN_REF`에 맞추는 채널 게인을 계산한다. 휘도는 보존한다.
   - 측정 크로마가 기준에서 너무 멀면 “피부가 아니다”라 보고 게인을 1로 둔다.
   - 게인이 클립 한계(`1/1.25 ~ 1.25`)를 넘으면 **적용하지 않는다.**
     클립된 게인을 적용하면 흰 셔츠가 민트색이 되는 사례가 확인되었다(코드 주석의
     images10). 확신 없는 보정은 하지 않는 쪽이 낫다.
2. **피부색**<br>
   수염/입술/긴머리가 섞이는 아랫볼 대신 코와 윗볼의 밝은 60%를 본다. 피부다운
   난색(R>G>B)만 통과시키고, 밝기와 채도를 함께 점수화해 회색 하이라이트를 피한다.
   너무 어두우면 기존 아랫볼 표본으로 폴백한다.
3. **대표색 군집화**<br>
   RGB를 6×6×6 칸으로 양자화하고, 가장 큰 군집의 중앙값을 대표색으로 쓴다.
   점유율이 18% 미만이면 `confident=False`가 된다.
4. **그림자/배경 회피**<br>
   영역의 밝은 상위 20~40%만 사용해 그림자를 줄이고, 테두리 4px 프레임에서 배경
   크로마/휘도를 추정한다. 헤어와 겉옷 표본에서는 배경과 비슷한 색을 탈락시킨다.
5. **상의/하의 밴드**<br>
   얼굴 아래에 상의 밴드 3개, 그 아래에 하의 밴드 2개를 놓고 “밴드별 최빈값의
   최빈값”을 고른다. 하의가 비었거나, 배경을 쟀거나, 상의를 그대로 다시 쟀으면
   프레임 하부 밴드로 재시도하고, 마지막으로 다리 영역의 전경 픽셀을 본다.
6. **마스크 국소화**<br>
   SCHP가 Pants/Skirt 픽셀을 주면 그 영역의 대표색이 하의 밴드 결과를 대체한다.
   Skirt와 Dress는 각각 별도 표본(`skirt_sample`, `dress_sample`)으로도 보관해
   치마/드레스 결정에 쓴다. 머리도 Hair 픽셀에서, 신발도 Shoes 픽셀에서 읽는다.
7. **줄무늬/원단**<br>
   두 번째 색의 점유율과 방향(세로/가로)을 재고, 줄무늬 두께를 1~3px로 측정한다.
   복잡 무늬는 사진의 천 패치를 크롭해 8×12/4×12 타일로 양자화한다.
8. **추가 표본**<br>
   홍채(눈 밴드의 어두운 픽셀), 안쪽 옷/타이(목 아래 칼라 영역), 겉옷(배경 제거),
   신발을 별도로 읽는다.

**출력**<br>
`ObservedColors`: 각 `ColorSample`(hex, 점유율, confident, rgb, 픽셀 수), WB 게인,
`top_alt`/`stripe`/`stripe_px`, `cover`, `bottom_plausible`, 하체 증거
(`lower_body_clothed`, `lower_body_bare`, `fullbody`), 치마 밑단/표본, 원단 텍스처,
`hair_stencil` 등.

**중요한 제약**

- **WB는 피부 앵커가 피부일 때만 적용된다.** 얼굴이 붉거나 작으면 게인을 1로 둔다.
- **마스크로 국소화한 색은 WB 이전 원본에서 잰다.** 마스크 자체가 옷을 고르므로
  색까지 WB로 밀면 과보정될 수 있기 때문이다. 반면 밴드/피부는 WB 적용 공간에서
  잰다. 같은 사진에서도 증거의 성격에 따라 색 공간을 다르게 쓰는 것이다.
- 갈색/베이지 셔츠는 피부와 크로마가 비슷하다. 그래서 의상에는 크로마 탈락을 쓰지
  않고, 공간 인셋과 점유율로 대신한다.
- `bottom_plausible`은 “측정값이 피부도 배경도 아니다”를 뜻한다. 맨다리를 잰 경우
  피부색을 유지하는 것이 맞으므로, 피부를 이유로 탈락시키지 않는다.
- 포즈가 없으므로 `measure_cover`는 웹에서 사실상 기권 상태다. 소매/하의 길이는
  VLM 값과 기본 정책이 맡는다.

### 3.5 S3 — 렌더: “64×64 픽셀로 어떻게 다시 그리는가?”

**목적**<br>
측정값과 분류값을 64×64 아틀라스에 결정론적으로 그린다. 사진을 그대로 옮기는 것이
아니라, 정해진 규칙으로 **다시 그리는** 단계다.

**입력**<br>
`ObservedColors`, `Attributes`, degrade 플래그, 모델(classic/slim), 노이즈 설정.

**처리**

1. **색 결정**<br>
   점유율이 낮은 표본은 기본색으로 대체한다. 재킷/레이어드 상의는 배경을 제거한
   겉옷 표본을 우선한다. 타이는 실제로 측정된 경우에만 그린다.
2. **하의 정책**<br>
   VLM의 유효한 하의 값이 있으면 그것을 쓰되, `none`은 곧바로 “맨다리”로 확정하지
   않고 증거 정책으로 재해석한다. VLM 값이 없거나 무효면 커버 측정 → 마스크/구도
   증거 → 기본값 순서로 내려간다.
   - 드레스: 다리 전체를 드레스 천으로 덮는다.
   - 치마: 측정된 밑단까지만 치마색, 그 아래는 맨다리.
   - VLM 하의 없음 + 파서가 옷을 봄 → 그럴듯한 측정색이면 측정 바지, 아니면 jeans.
   - VLM 하의 없음 + 파서가 맨다리를 봄 → 맨다리.
   - 상반신/판단 불가 → **jeans 기본값**.
   - 전신인데 증거가 없음 → 피부 유지.
3. **무늬/원단**<br>
   VLM이 확신하는 plain은 측정 줄무늬를 끈다. 화질 저하 플래그가 있으면 plain/측정
   줄무늬 쪽으로 보수화한다. 상의는 VLM이 복잡 무늬(plaid/check/graphic/floral)라고
   한 경우에만 크롭 원단을 쓰고, 하의는 고주파 복잡도 게이트를 통과할 때만 쓴다.
   그 외에는 측정된 패턴 두께(기본 1px)로 그린다.
4. **구조**<br>
   VLM 구조 태그가 있을 때만 지퍼/단추/칼라/패치 주머니를 1px로 얹는다. 셔츠 칼라인데
   여밈 태그가 없으면 단추로 보수적으로 보정하고, 지퍼를 임의로 그리지는 않는다.
5. **머리**<br>
   `assets/reference_pack.json`이 L1 실루엣(short/long 스켈레톤)·L1 음영 톤·L2 마스크·
   긴 머리 몸통 드레이프를 제공한다. 사진의 SCHP/규칙 스텐실은 대머리·길이·앞머리
   증거로만 쓰고, 실루엣은 reference가 소유한다(2026-11-01). `hair_style`이 없거나
   무효면 길이에서 폴백한다. loose 스타일은 눈썹 행(4)을 덮고 눈(5~6행)은 덮지 않는다.
   L2는 solid 셸이 아니라 참조 마스크(프린지/가닥)이며 L1과 같은 톤을 쓴다. 후드는
   L2로 헤드/어깨에 그리되 노이즈 뒤에 그린다. head bottom은 Minecraft 규약대로
   texture row 7이 턱이다(§8).
6. **팔다리/신발**<br>
   소매 길이, 하의 종류, 신발 2톤을 적용한다. 각 후보의 신발 2톤/단색(flat) 쌍은
   같은 시드로 렌더하고, L2 오버레이는 `hair_overlay` 옵션을 따른다.
7. **노이즈**<br>
   면 단위 결정론적 시드로 1~3px 불규칙 톤 밴딩을 넣는다. 같은 후보는 항상 같은
   텍스처가 나오고, 세기 0은 무노이즈와 바이트 동일하다. reference 음영을 넣은 머리
   픽셀은 노이즈에서 제외해 가닥을 보존한다.

**출력**<br>
`SkinCanvas`(64×64 RGBA 이미지)와 그 변형(신발 단색 flat).

**중요한 제약**

- HEAD L1은 reference 스켈레톤과 음영 톤을 따르고, L2는 참조 마스크(프린지/가닥)를
  L1 위에 얹는다. L2 톤은 아래 L1 셀과 같게 두고(참조 비율 1.00), 볼륨은 마스크
  모양으로 만든다. solid 셸은 참조와 어긋나며(§8), 2026-11-01 이전 동작이다.
- 왼팔/왼다리는 캔버스 `put` 단계에서 미러링된다. 렌더 코드는 좌우를 같은 좌표로
  그려야 한다.
- 노이즈는 좌우 비대칭을 허용하지만, 검증은 `NOISE_TOL` 이내만 통과시킨다.
- 색/정책의 우선순위는 코드에 명시되어 있다. “측정값이 있으면 무조건 이긴다”가
  아니라, **확신도와 증거 종류**에 따라 달라진다.

### 3.6 S4 — 후보: “불확실한 부분을 숨기지 말고 보여주자”

**목적**<br>
VLM의 두 응답이 어긋난 필드만 변형해 1~3개의 후보를 만든다. 랭킹은 하지 않는다.

**입력**<br>
`ObservedColors`, `Classification`.

**처리**

- c1은 첫 응답 그대로다.
- 변형 가능 필드는 `top_garment`, `hair_length`, `sleeve_len`으로 제한된다.
- 두 번째 응답에서 유효했던 값만 후보 근거로 쓴다. 강제/누락된 값은 근거가 아니다.
- 교차 규칙을 다시 적용하고, 중복 후보는 제거한다. 최대 3개.
- 후보별로 색/속성/degrade/순번에서 결정론적 노이즈 시드를 파생한다.
- 각 후보는 ON/OFF 두 변형을 렌더하고 **모두** `validate_image`를 통과해야 한다.

**출력**<br>
`Candidate` 리스트. 각 후보는 이미지, flat 이미지, 변형 사유, 시드, 문제 목록을 갖는다.

**중요한 제약**

- 근거 없는 변형(임의 enum 순환)은 만들지 않는다.
- 후보가 하나라도 검증에 실패하면 API는 500 `render_failed`로 실패한다. 품질 게이트를
  통과한 것만 사용자에게 보여준다.
- 후보가 여러 개라는 것은 “정답이 여러 개”가 아니라 “이 필드는 확신할 수 없다”는
  정직한 표시다.

---

### 3.7 검증·저장·표시

**검증**<br>
`skinmaker/validate.py`의 `validate_image`가 다음을 확인한다.

- 크기 64×64, 모드 RGBA.
- 사용하지 않는 픽셀이 투명한가(bleed 방지).
- L1(내곽) 레이어가 완전 불투명한가.
- 좌우 미러가 `NOISE_TOL` 이내인가.

**저장/응답**<br>
입력 사진, 후보 PNG, flat PNG, 처리 과정 시트를 `backend/static/`에 저장하고 URL로
돌려준다. 응답에는 요약 문자열, 14개 속성 값, `uncertain`/`derived`/`coerced`,
후보별 변형 사유, 사용된 `noise_level`, `skin_model`, `hair_overlay`, steps URL이
포함된다(`hair_source`/`hair_symmetry`는 2026-11 제거 — §8).

**웹**<br>
React가 결과를 인라인으로 보여주고(완성 미리보기 모달 없음), 3D 뷰어(마우스 전용 회전·
고정 고휘도 조명), 편집 모달(신발 2톤), 분류 카테고리 패널, 처리 과정 시트를 제공한다.
모바일에서 결과가 뷰포트 아래면 자동 스크롤한다. 3D 지오메트리는
`frontend/src/skinModel.js`를 통해 QA 렌더 하네스와 공유한다.

**운영 가드**<br>
공개 데모 기준 업로드 15MB, IP당 분당 6회, 14일 보존. 얼굴 없음은 422, 용량 초과는
413, 레이트리밋은 429, AI 설정 누락은 503, 렌더 검증 실패는 500으로 구분한다.

## 4. 왜 보정이 필요한가

### 4.1 근본적인 불일치

이 파이프라인에는 처음부터 세 가지 불일치가 있다.

1. **입력은 연속적이고 통제되지 않는다.** 조명, 화이트밸런스, 그림자, 배경, 구도,
   해상도, 압축, 가림이 모두 제각각이다.
2. **출력은 이산적이고 극단적으로 작다.** 64×64, 레이어당 1,632픽셀, 얼굴 64픽셀.
   한 픽셀 오차가 표정과 옷의 인상을 바꾼다.
3. **VLM은 의미를 잘하지만 측정을 못한다.** “재킷”은 잘 맞히지만 “정확히 어떤
   색인지”, “그 옷이 몇 번째 행까지 내려오는지”는 믿기 어렵다.

보정은 이 세 세계 사이의 **통역**이다. 사진의 픽셀을 그대로 축소하는 것이 아니라,
사진에서 **믿을 수 있는 증거**를 뽑아 64×64의 좌표·색·의미 체계로 옮기고, 증거가
약하면 “모른다”고 말하게 만든다.

### 4.2 보정의 다섯 층

| 층 | 질문 | 대표 장치 | 보정이 없으면 |
|---|---|---|---|
| 색 보정 | “이 색이 정말 그 색인가?” | 피부 앵커 WB, 밝은 백분위, 배경 크로마/휘도 제거, 마스크 색은 raw로 측정 | 조명 색이 모든 옷에 곱해지고, 그림자/배경이 옷 색으로 측정된다 |
| 공간 보정 | “이 영역이 정말 그 부위인가?” | 얼굴 기준 크롭, 전신 임계값, SCHP 마스크, bbox 역변환, 치마 밑단 정규화, reference 스켈레톤 | 하의 대신 셔츠 꼬리를 재거나, 치마가 미니로 그려지거나, 머리카락에 구멍이 난다 |
| 의미 보정 | “이 조합이 논리적으로 가능한가?” | enum 검증, 기본값, 교차 규칙, 이중 질의 합의, 불확실성 | `top=none`인데 소매가 생기고, 모순된 필드가 렌더러로 내려간다 |
| 확신/정책 보정 | “이 값을 믿어도 되는가?” | 점유율 18% 게이트, `bottom_plausible`, 폴백 우선순위, 보수적 패턴/구조 | 2%짜리 배경색이 머리색이 되고, 근거 없는 지퍼/무늬가 그려진다 |
| 출력 보정/검증 | “게임에서 깨지지 않는가?” | UV 레이아웃, 미러, 알파, bleed 검사, 노이즈 허용 오차 | 투명한 몸통, 겹친 면, 좌우가 다른 팔, 게임에서 깨지는 스킨 |

### 4.3 보정이 없을 때 실제로 일어나는 일

- **색이 전부 틀어진다.** 따뜻한 백열등 아래에서 찍은 사진은 모든 색이 노랗게
  편향된다. WB를 하지 않으면 흰 셔츠가 크림색, 회색 바지가 갈색이 된다. 반대로
  클립된 게인을 무조건 적용하면 흰 셔츠가 민트색이 된다. 그래서 “보정하되, 확신
  없으면 하지 않는다”가 필요하다.
- **그림자와 배경이 옷으로 둔갑한다.** 얼굴 아래 밴드가 배경 벽이나 셔츠 그림자를
  잡으면, 하의가 회색 벽색이 되거나 상의가 하의로 복제된다. 배경 크로마/휘도 거부,
  밴드 재시도, 마스크 국소화가 이걸 막는다.
- **부위를 잘못 자른다.** 얼굴 비례만으로 하의를 찾으면 앉은 자세/전신에서 옷이
  프레임 밖으로 나간다. 크롭을 넓히고, 전신 기준을 공유하고, SCHP 마스크로 위치를
  확정하는 이유다.
- **의미가 모순된다.** VLM이 “상의 없음”과 “긴 소매”를 동시에 말할 수 있다. 교차
  규칙이 없으면 맨 어깨에 소매가 그려진다.
- **하나의 답을 정답처럼 쓴다.** VLM은 같은 사진에도 조금씩 다르게 답한다. 이중
  질의와 불확실성 표시, 후보 생성이 없으면 우연히 첫 번째로 나온 답이 그대로
  사용자에게 간다.
- **64×64 규격이 깨진다.** UV 밖에 픽셀을 쓰거나, L1을 투명하게 두거나, 좌우를
  다르게 그리면 게임에서 스킨이 깨진다. `validate_image`는 이 사고를 저장 직전에
  막는 마지막 보정/검증 층이다.

### 4.4 한 장의 사진으로 따라가 보기

상황을 하나 가정하자. **(추론이 아니라 설명을 위한 시나리오다.)**

> 형광등이 섞인 실내에서 찍은 상반신 사진. 흰 셔츠, 청바지, 회색 벽.
> 사진은 살짝 초록빛이 돌고, 셔츠 하이라이트는 날아갔고, 하의는 프레임 아래로
> 잘려 있다.

1. **S0**은 얼굴을 찾고 “작은 얼굴/약간 흐림” 플래그를 붙인다. 거부하지 않는다.
2. **S2**는 “셔츠, 하의 없음, plain, 긴 소매”라고 답한다. 하의가 프레임에 없으니
   `bottom=none`은 사진에 충실한 답이다.
3. **S1의 WB**는 볼/코의 피부 크로마를 기준으로 초록빛을 줄인다. 게인이 클립 한계를
   넘으면 아예 적용하지 않아, 흰 셔츠가 민트색으로 가는 것을 막는다.
4. **S1의 하의 밴드**는 얼굴 아래를 보지만 셔츠 꼬리나 벽을 잡을 수 있다. 밴드 결과가
   상의와 같거나 배경과 같으면 프레임 하부로 재시도하고, 그래도 안 되면 SCHP 마스크를
   본다. 마스크에도 하의가 없으면 “하의 미관측”으로 남긴다.
5. **S3의 하의 정책**은 `bottom=none`을 그대로 믿지 않는다. 파서가 옷을 봤으면 측정
   바지를, 맨다리를 봤으면 맨다리를, 아무 증거가 없고 상반신이면 **jeans 기본값**을
   쓴다. 이 사진은 상반신이므로 청바지가 그려진다. 만약 전신인데 하의 증거가 전혀
   없다면 피부를 유지한다.
6. **S3의 패턴**은 VLM이 plain이라고 확신하면 측정 줄무늬를 끈다. 흰 셔츠의 주름을
   줄무늬로 착각하지 않게 하는 보수화다.
7. **S4**는 두 번째 질의가 “반팔”이라고 답했다면 소매 후보를 하나 더 만든다. 두 답이
   같으면 후보는 하나다.
8. **검증**은 64×64, RGBA, L1 불투명, 미러, bleed를 확인한다. 통과한 후보만 저장된다.

이 과정에서 **보정이 하는 일은 “더 예쁘게”가 아니라 “더 방어적으로”**다. 확신이 있으면
그 값을 쓰고, 없으면 기본값으로 물러나며, 절대 사진에 없는 디테일을 지어내지 않는다.

### 4.5 보정은 파이프라인 전체를 연결한다

보정은 한 함수에 모여 있지 않다. 각 단계가 **증거와 확신**을 다음 단계로 넘기고,
다음 단계가 그 증거의 종류에 따라 다르게 반응한다.

```
ColorSample(share, confident) ─┐
bottom_plausible ──────────────┼→ resolve_colors / resolve_bottom_ex
lower_body_clothed/bare ────────┤   (VLM > 측정 > 증거 > 기본값)
fullbody ──────────────────────┘
Attributes(coerced/missing) ───→ uncertain ─→ 후보 변형 + UI 표시
HairStencil(마스크/규칙) ───────→ render_head / render_hair_overlay
validate_image ─────────────────→ 저장 전 최종 게이트 (실패 시 500)
```

즉, 보정은 “중간에 한 번 색을 보정하는 단계”가 아니라 **파이프라인의 계약**이다.
상류에서 만든 확신도가 하류의 결정을 바꾸고, 하류의 검증이 상류의 실수를 잡는다.

### 4.6 보정이 해결하지 못하는 것

- 사진에 없는 정보(가려진 발, 모자 아래 머리, 뒤통수)는 복원할 수 없다. 그래서
  “그럴듯한 기본값”과 “모른다”를 구분한다.
- VLM의 의미 오분류(폴로/셔츠/탱크 구분)는 여전히 약점이다.
- 64×64에서 플로럴/플레이드의 디테일을 완전히 살릴 수는 없다. 크롭 원단은 “느낌”을
  살리는 대체물이지 원본 복원이 아니다.
- 포즈가 없으므로 소매/하의 길이의 커버 측정은 사실상 비활성이다. 현재는 VLM과
  기본 정책이 그 자리를 메운다.
- 주관적 “닮음”은 자동 검증으로 끝나지 않는다. `qarender`, `score`, `hairreport` 같은
  QA 도구와 사람의 시각 검토가 별도로 필요하다.

## 5. 핵심 계약/주의사항

이 목록은 “깨지면 파이프라인이 조용히 망가지는 것”들이다.

1. **64×64 UV 레이아웃의 단일 원천은 `skinmaker/format.py`다.**<br>
   `Layout.check()`가 면 겹침, 경계, 사용 가능 픽셀 수를 자체 검증한다.
   classic은 레이어당 1,632픽셀, slim은 1,568픽셀이다. 프론트의 UV 상수는
   `frontend/src/skinModel.js`에 있고, `test_render.py`가 두 레이아웃을 대조한다.

2. **왼팔/왼다리 미러는 캔버스 계층에서 강제된다.**<br>
   `SkinCanvas.put()`이 왼쪽 파트의 u를 뒤집는다. 렌더 코드가 좌우를 따로 그리면
   미러가 깨진다. 검증은 `NOISE_TOL` 이내만 허용한다.

3. **L1은 완전 불투명, 사용하지 않는 픽셀은 투명해야 한다.**<br>
   L1에 알파 구멍이 있거나 UV 밖에 픽셀을 쓰면 게임에서 깨진다. `validate_image`가
   저장 전에 막는다.

4. **노이즈는 결정론적이어야 한다.**<br>
   시드는 색/속성/degrade/후보 순번에서 파생된다. 같은 후보는 항상 같은 텍스처여야
   하고, `noise_level=0`은 무노이즈와 바이트 동일해야 한다. 시드 입력을 바꾸면
   재현성 계약이 깨진다.

5. **VLM은 의미만 담당한다.**<br>
   색 필드를 스키마에 넣지 않는다. 색은 코드가 잰다. 이 분리가 “회색 셔츠를 네이비로
   부르는” 문제를 막는 핵심이다.

6. **유일한 하드 거부는 얼굴 미검출이다.**<br>
   품질 플래그는 거부가 아니라 렌더 파라미터다. 얼굴이 없을 때만 422로 끝낸다.

7. **폴백은 “실패”가 아니라 설계다.**<br>
   SCHP 없음 → 밴드, VLM 두 번째 실패 → 단일 질의, 확신 없는 색 → 기본색, 하의
   미관측 → 정책 기본값. 각 폴백은 왜 그 기본값이 안전한지 코드 주석에 근거가 있다.

8. **후보 변형은 증거가 있을 때만 한다.**<br>
   두 번째 질의에서 유효했던 값, 그리고 변형 가능 필드(`top_garment`, `hair_length`,
   `sleeve_len`)만. 근거 없는 enum 순환은 금지된다.

9. **마스크는 요청당 한 번만 추론한다.**<br>
   색 추출, 처리 과정 시트, 머리 스텐실이 같은 `seg`를 공유한다. 같은 요청 안에서
   서로 다른 마스크를 보면 색과 시각 자료가 어긋난다.

10. **공개 배포 가드를 약화시키지 않는다.**<br>
    업로드 15MB, IP당 분당 6회, 14일 보존. 인증이 없는 공개 데모의 최소 방어선이다.

11. **테스트와 린트를 통과해야 한다.**<br>
    현재 `pytest -q` 675개, 프론트는 `npm run lint` / `npm run build`. 시각 변경은
    `qarender`로 전후를 남기는 것이 권장된다.

## 6. 한눈에 이해하기

### 6.1 비유: “64×64 도트 그림으로 번역하는 팀”

- **VLM**은 “이 사람이 무엇을 입었는지”를 말하는 통역사다. 말은 잘하지만 숫자에는 약하다.
- **SCHP**는 “그 옷이 사진 어디에 있는지”를 짚는 안내자다.
- **색 측정기**는 “그 옷이 정확히 어떤 색인지”를 재는 계측기다. 조명이 바뀌면
  기준을 다시 잡아야 한다.
- **렌더러**는 64×64라는 캔버스에 맞춰 그리는 도트 디자이너다.
- **검증기**는 “게임에서 이 스킨이 깨지지 않는지” 보는 QA다.
- **보정**은 이들이 서로 다른 단위(사진 픽셀, 0~1000 bbox, 8×8 격자, 0~255 색)로
  말하지 않도록 맞추는 **교정 회의**다. 회의에서 “모르겠다”라고 말할 수 있어야
  엉뚱한 픽셀을 칠하지 않는다.

### 6.2 60초 요약표

| 단계 | 한 줄 질문 | 핵심 장치 | 결과 |
|---|---|---|---|
| S0 | 이 사진을 쓸 수 있나? | YuNet, 품질 플래그 | 얼굴 상자 + degrade |
| S2 | 무엇을 입었나? | VLM 2회, 14 enum, 이중 질의 | 속성 + 불확실성 + hair_bbox |
| S1b | 그 부위가 어디 있나? | SCHP 마스크 | 부위별 픽셀 지도 |
| S1 | 무슨 색인가? | 피부 앵커 WB, 군집, 배경 제거, 캐스케이드 | 색 + 증거 + 확신도 |
| S3 | 어떻게 그릴까? | 우선순위/폴백, 패턴/구조/머리 규칙 | 64×64 픽셀 |
| S4 | 얼마나 확실한가? | 불일치 필드만 변형 | 1~3 후보 |
| 검증 | 게임에서 안 깨지나? | UV/미러/알파/bleed | 통과한 PNG만 저장 |

### 6.3 한 문장 요약

> **스킨메이커는 사진을 축소하는 시스템이 아니라, 사진에서 믿을 수 있는 증거만 뽑아
> 64×64의 제한된 문법으로 다시 그리는 시스템이며, 보정은 그 증거를 신뢰할 수 있는
> 좌표·색·의미로 바꾸고, 확신이 없을 때 기권하게 만드는 장치다.**
